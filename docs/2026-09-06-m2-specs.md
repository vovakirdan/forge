# M2: engineering Pipeline, Employee concurrency and Inbox

Status: approved implementation direction; acceptance is tracked separately in
[the task breakdown](2026-09-06-m2-tasks.md). M0–M1 remain closed.

## Scope

The current M2 provider matrix is Codex CLI, Claude Code CLI with subscription
authentication, OpenRouter API and OpenAI API. API access reuses OpenCode and
Provider Gateway. Cursor, Gemini, Grok Build CLI and Claude CLI API-key auth are
deferred, not declared implemented. Linux/local deployment and CLI/API remain
the target; no UI, remote control plane, hosted PR/MR integration or M3 knowledge
projection is added here.

## Employee and execution

Employee identity is not a process. Versioned Employee configuration determines
eligibility, prompts, permissions and concurrent capacity; a Run freezes its
configuration. Multiple Task Runs of one Employee have different workspaces,
provider sessions, private homes, credentials snapshots and fences. Existing
profiles retain capacity one until explicitly changed.

Execution authority comes from a typed assignment: Task stage, project hook,
resolution or communication. Communication need not reference a Task. A context
reference is not permission to execute that Task's stage. System work does not
require a fake Employee. Admission accounts for Employee, Project, host and
credential/account limits; resource claims survive logical revocation until
physical quiescence. There is at most one writer per TaskWorkSurface.

Pipeline versions remain immutable. Publishing a new default affects new Task
bindings only. Soft deletion preserves historical versions and references.
Stage instructions and workspace requirements are pinned with the Pipeline.

## Git and acceptance

Task owns its repository binding, initial base, candidate and retained surface.
Employee changes never select a different source. Interrupted work is retained;
Forge does not implicitly add files, commit, reset or erase it.

A Git-writing submission proposes an explicitly committed candidate. Final
acceptance follows confirmed writer quiescence, HEAD validation and a clean
tracked/untracked tree. Read-only review and QA copies are created from the
accepted commit, without ignored leftovers. Artifacts and acceptance records
identify the examined revision. Independence checks use all contributing
Employee identities recorded by Core, not forgeable Git authors.

QA is an Employee activity, not a built-in automatic test runner. Report-only
QA may use a disposable copy. Explicitly assigned test development receives a
writer assignment and produces a new candidate requiring its configured gates.
Review, rework and QA retain the same Task.

Project hooks are explicit optional configuration: command, execution image,
trigger/applicability, timeout and required/advisory policy. Missing or
inapplicable hooks do not block. Forge does not discover test frameworks or
implicitly execute repository hooks. Required results cannot be waived through
an Employee's prose.

Local integration preserves commits with a merge commit. Target must be an
ancestor of the accepted candidate; the merge has exactly the candidate tree.
Otherwise the same Task follows a configured stale-base outcome and produces
a newly accepted revision. No hidden semantic merge/rebase follows approval.

Only the trusted integration backend writes the target. Persist the exact merge
SHA and expected target before CAS; serialize by physical Git common-dir/ref.
Recovery checks target ancestry, not a receipt marker alone. Unknown state is
held for reconciliation, never overwritten or silently declared done.
Checked-out target branches, including linked worktrees, are rejected. Owners
must not perform concurrent external checkout/worktree operations during
integration; a Forge lock does not lock an owner's shell.

## Communication

Employee Inbox exists independently of Task. Messages are immutable and have
stable IDs, ordered thread context, sender and recipient. Persist the message,
audit and delivery intent atomically; existing outbox/NATS wakes delivery,
PostgreSQL owns truth.

Direct instructions address Employee plus Task execution context, or an exact
fenced Run. General questions/mentions run in a separate CommunicationAssignment
without interrupting unrelated work. A mention is not a Task assignment; a new
Task is admitted by the scheduler. Communication can read allowed context,
reply and escalate, but does not inherit another Run's writer or stage rights.

Distinguish persisted, runtime-accepted, Employee-acknowledged and answered.
At-least-once delivery with deduplicated canonical replies is not exactly-once
LLM processing. Direct required instructions accepted before final outcome
must satisfy their receipt requirement in the same serialized acceptance check.
A stopped Run cannot acknowledge a late message. Messages after acceptance do
not retroactively revoke the outcome. Pending input survives recovery.

Runtime drivers support subsequent input in the same live session. A model turn
is not necessarily Run completion; input does not reset Run budgets. Immediate
mid-generation interruption is not guaranteed. Emergency stop remains a named
operation independent of whether an LLM reads a message.

Project stop closes admission and stops all execution purposes. Incoming
messages, human management, audit and reconciliation remain available without
launching new processing Runs.

## Acceptance boundary

Use an isolated real Git fixture, never Forge or a user project. Prove two Task
Runs plus one taskless Communication Run for the same Employee, targeted direct
input, review/rework and both QA modes, no-hook success, configured hook failures,
stale revisions, target movement, conflicts, crash/retry, stop and resolver
failover. Preserve M0–M1 conformance and test every RunSpec version through
recovery, inventory, credential writeback and cleanup.

Each of the four provider profiles needs explicit opt-in live proof in addition
to synthetic conformance. Unavailable credentials or unrun live checks are
reported as unverified, not converted into successful acceptance.

## Resolution authority clarification

An escalation answer is authoritative for its bounded technical question, not
an Employee-stage completion. `continue_stage` resolves only its own escalation
wait; `needs_management_change` requires a separate management command;
`forward_to_human` replaces the resolver generation. A recommended outcome key
must exist in the pinned stage but does not apply its transition. Dangerous
action approval defaults to Human; cancellation remains a named command with a
catalog reason. Communication escalation has its own typed source, never an
invented Task or authority derived from an optional context Task.

See [M2_RESOLVER_QUEUE.md](M2_RESOLVER_QUEUE.md) for contracts and the explicitly
bounded implementation checkpoints.
