# M2 Git outcome: предложение, проверка, принятие

Этот документ описывает реализованный переход от writer-отчёта к принятию
результата. Сам по себе он не означает готовность всего M2: независимое ревью,
QA, hooks и Core-managed Integration имеют отдельные условия приёмки.

## Контракт

У Task есть неизменяемая Git-привязка к ProjectRepository и постоянный surface.
Employee не выбирает другой source при передаче работы. Writer сам создаёт
commit; Forge не выполняет за него `git add`, commit, reset или очистку файлов.

В `outcome.submit` для Git writer обязателен `candidate_commit`: полный SHA-1
или SHA-256 commit. Core проверяет текущий Run/fence/epoch, PipelineVersion,
stage visit, артефакты и обязательные инструкции. Затем в одной транзакции
сохраняет неизменяемый GitStageProposal, событие и желаемую остановку Run.
Ответ `proposal_saved` означает только сохранённое предложение, не завершение
стадии. Task остаётся `in_progress`.

## Граница принятия

1. Supervisor подтверждает физическую остановку writer. До этого сохраняется
   физическая резервация; логический revoke сам по себе её не освобождает.
2. Core записывает точный InspectGitCandidate intent, затем отправляет его
   Supervisor. Потерянная отправка восстанавливается из PostgreSQL.
3. Supervisor проверяет host/boot, последний writer этого surface, положительную
   quiescence, host-owned manifest, ожидаемый HEAD и чистоту индекса/worktree.
   Незакоммиченные tracked/untracked файлы запрещают принятие. Ignored файлы не
   становятся частью результата. Выполнение host Git filters и gitlinks пока
   не поддерживается и отклоняется.
4. Core сохраняет наблюдение и проверенный candidate с Core-attributed writers.
   Повторно проверяет Task revision, stage visit, Project gate и обязательные
   сообщения — в той же Project-транзакции, что и финальный переход Pipeline.
5. Только после этих проверок завершаются старая очередь и стадия, появляется
   handoff и может быть поставлена в очередь следующая работа.

Inspection не продвигает остановленный Run по sequence и не возобновляет Lease.
У него собственные долговечные request/reply identities. История ответов
сохраняется и при повторных попытках. `Busy`/`Unavailable` допускают до трёх
попыток с новыми command IDs; потерянный ответ повторно запрашивается с прежним
ID. Ожидание ответа ограничено 90 секундами на попытку. Неизвестная quiescence,
смена host/boot и постоянный отказ требуют решения менеджера.

## Отказ и восстановление

При dirty HEAD, просроченной проверке или новой обязательной инструкции
предложение и файлы сохраняются. Текущая стадия получает `waiting/manual_pause`.
Устаревшая запись очереди освобождается отдельно от физической резервации;
менеджер может явно возобновить ту же Task новым Run. Старое предложение не
переписывается и не принимается автоматически после снятия ожидания.

Изменение Task revision делает предложение устаревшим. Core не применяет старый
outcome к другой стадии и не останавливает нового writer. Если изменились только
метаданные текущей стадии, Core оставляет явное ожидание для решения менеджера,
а не теряет Task между очередями.

Подтверждение текста артефакта не является проверкой его истинности. Инспекция
доказывает состояние Git, а не качество кода. Это остаётся обязанностью
настроенных стадий ревью/QA и человека.

## Проверки

`m2_git_proposal` проверяет PostgreSQL, реальный UDS Gateway и gRPC: предложение
до stop, отказ неверного fence, точное принятие после stop, позднюю инструкцию,
dirty → ожидание → новый Run, Busy с новой попыткой и replay старого ответа.
Supervisor filesystem-результаты в этом тесте синтетические; это не live LLM
или end-to-end Git proof. Отдельные GitBackend и Supervisor inspection tests
используют настоящие временные Git-репозитории, не пользовательский source.
